PHẦN 1: BỨC TRANH TOÀN CẢNH & MÔ HÌNH KIẾN TRÚC TỔNG THỂ
================================================================================

1.1. BÀI TOÁN THỰC TẾ CỦA DỰ ÁN
ThunderFood là hệ sinh thái kinh doanh F&B kết hợp logistics vận chuyển nội thành.
Hệ thống giải quyết 3 nhóm nhu cầu lớn tương ứng với 3 đối tượng người dùng:
  - KHÁCH HÀNG (Customer): Duyệt món ăn, xem đánh giá, áp mã voucher kép (giảm món
    + giảm ship), đặt hàng, theo dõi lộ trình đơn hàng.
  - NHÂN VIÊN VẬN HÀNH & SHIPPER (Staff): Quản lý bếp, xác nhận đơn, và đặc biệt
    là GOM ĐƠN THÀNH GÓI HÀNG (Delivery Package) để giao nhiều đơn theo lộ trình.
  - QUẢN TRỊ VIÊN (Admin): Xem báo cáo doanh thu KPI, quản lý thực đơn (món ăn,
    danh mục), quản lý kho voucher, cấu hình hệ thống (phí ship, freeship threshold).

1.2. MÔ HÌNH KIẾN TRÚC PHÂN TẦNG (LAYERED ARCHITECTURE)
Backend ThunderFood được xây dựng theo chuẩn Kiến Trúc Phân Tầng (N-Tier Architecture),
với nguyên tắc "Phân tách mối quan tâm" (Separation of Concerns):

   [ CLIENT REQUEST ] (Web Customer / Admin Portal / Staff App)
          │
          ▼
   [ 1. SECURITY & FILTER LAYER ]
   (CorsFilter -> JwtAuthenticationFilter -> SecurityFilterChain)
          │ (Hợp lệ / Có quyền)
          ▼
   [ 2. PRESENTATION / CONTROLLER LAYER ]
   (AuthController, ProductController, CartController, OrderController...)
   - Tiếp nhận HTTP Request (GET/POST/PUT/DELETE)
   - Kiểm tra dữ liệu đầu vào (Validation với Jakarta/Hibernate Validator)
   - Điều hướng sang tầng Service
          │
          ▼
   [ 3. BUSINESS / SERVICE LAYER ]
   (OrderService, ProductService, CartService, AuthService, VoucherService...)
   - Chứa 100% logic nghiệp vụ cốt lõi và thuật toán
   - Quản lý giao dịch dữ liệu (@Transactional)
   - Tính toán chi phí, trừ tồn kho, tính hạn mức voucher, gom gói đơn hàng
          │
          ▼
   [ 4. DATA ACCESS / REPOSITORY LAYER ]
   (OrderRepository, ProductRepository, CartRepository, UserRepository...)
   - Kế thừa Spring Data JPA (JpaRepository)
   - Giao tiếp với Cơ sở dữ liệu, thực hiện truy vấn CRUD, Derived Queries, JPQL
          │
          ▼
   [ 5. DATABASE LAYER ]
   (MySQL Database: Bảng orders, products, users, delivery_packages, vouchers...)

1.3. CƠ CHẾ STATELESS API
Hệ thống không lưu trữ Session trên server (SessionCreationPolicy.STATELESS). Mọi
request từ client gửi lên đều độc lập và phải đính kèm JWT (JSON Web Token) ở
Header `Authorization: Bearer <token>`. Điều này giúp Backend dễ dàng mở rộng
quy mô (Scale out) chạy trên nhiều container/server mà không sợ mất phiên đăng nhập.

PHẦN 2: HỆ SINH THÁI CÔNG NGHỆ (TECH STACK)
================================================================================

2.1. JAVA 21 & SPRING BOOT
  - Java 21 (LTS): Phiên bản Java hiện đại, hiệu năng cao, hỗ trợ cú pháp ngắn gọn,
    Pattern Matching, Virtual Threads.
  - Spring Boot 4.x / 3.x Starter: Framework số 1 cho Java Backend, tự động cấu
    hình (Auto-Configuration), nhúng sẵn Tomcat Server, quản lý vòng đời Bean (IoC/DI).

2.2. SPRING SECURITY & JWT (JJWT 0.11.5)
  - Spring Security 6+: Bảo mật đa tầng, phân quyền theo vai trò (Role-Based Access
    Control: ROLE_CUSTOMER, ROLE_ADMIN, ROLE_STAFF).
  - JJWT: Mã hóa, ký và xác thực token JWT chuẩn HMAC-SHA256.
  - Cơ chế Token Kép (Dual-Token Strategy):
    + Access Token: Thời gian sống ngắn (1 ngày = 86400000ms), dùng gọi API thường nhật.
    + Refresh Token: Thời gian sống dài (7 ngày = 604800000ms), lưu trữ trong bảng
      `user_tokens`, dùng để cấp mới Access Token mà không bắt người dùng đăng nhập lại.

2.3. SPRING DATA JPA & HIBERNATE & MYSQL
  - Spring Data JPA: Giảm thiểu 90% code truy vấn boilerplate. Chỉ cần khai báo
    Interface là Spring tự sinh mã SQL tương ứng.
  - Hibernate: Công cụ ORM (Object-Relational Mapping), ánh xạ Class Java thành bảng
    MySQL và ngược lại.
  - Hibernate ddl-auto: update (Tự động cập nhật schema bảng theo các Entity Java).

2.4. CLOUDINARY SDK
  - Thư viện tích hợp lưu trữ đám mây cho hình ảnh món ăn, banner, avatar.
  - Backend nhận file Multipart từ Client -> Tải lên Cloudinary -> Nhận link CDN
    HTTPS trả về lưu vào database.

2.5. SPRING MAIL (GMAIL SMTP)
  - Gửi email bất đồng bộ phục vụ tính năng Quên mật khẩu / Gửi mã OTP xác thực.

2.6. SPRINGDOC OPENAPI (SWAGGER UI)
  - Tự động sinh tài liệu API trực quan tại `/swagger-ui/index.html`. Cho phép
    Frontend team tra cứu định dạng Request/Response và bấm chạy thử API trực tiếp.

2.7. LOMBOK
  - Thư viện tự động sinh Constructor, Getter, Setter, Builder Pattern thông qua
    các annotation (`@Getter`, `@Setter`, `@Builder`, `@RequiredArgsConstructor`),
    giúp code Java gọn gàng, trong sáng.

PHẦN 4: GIẢI MÃ VAI TRÒ VÀ CHỨC NĂNG CỦA CÁC LOẠI FILE
================================================================================

Để trở thành lập trình viên backend vững vàng, bạn cần hiểu rõ "Triết lý trách nhiệm"
của từng loại file trong kiến trúc phân tầng:

4.1. CONTROLLER (*Controller.java)
  - VAI TRÒ: "Người gác cửa" của hệ thống API.
  - NHIỆM VỤ:
    + Định tuyến URL qua `@GetMapping`, `@PostMapping`, `@PutMapping`, `@DeleteMapping`.
    + Nhận Request Body, Path Variables, Query Params.
    + Kích hoạt xác thực hợp lệ bằng `@Valid` (bắt lỗi nếu email sai, giá âm...).
    + Gọi duy nhất 1-2 hàm tương ứng ở tầng Service.
    + Đóng gói kết quả vào `ApiResponse<T>` chuẩn và trả về HTTP Status code thích hợp
      (200 OK, 201 Created, 204 No Content).
  - NGUYÊN TẮC: Controller KHÔNG ĐƯỢC CHỨA LOGIC NGHIỆP VỤ (No business logic in controllers).

4.2. DTO (Data Transfer Object)
  - VAI TRÒ: "Hợp đồng dữ liệu" giữa Client và Server.
  - TẠI SAO PHẢI CÓ DTO MÀ KHÔNG DÙNG TRỰC TIẾP ENTITY?
    + Bảo mật: Tránh lộ thông tin nhạy cảm của Entity (ví dụ: trường `password` trong User).
    + Ngăn ngừa Over-posting: Tránh việc hacker gửi đè trường `role=ADMIN` khi cập nhật profile.
    + Tối ưu băng thông: Chỉ gửi những trường Frontend thật sự cần hiển thị.
  - PHÂN LOẠI DTO TRONG DỰ ÁN:
    + Request DTOs (vd: `LoginRequest`, `PlaceOrderRequest`, `ProductCreateRequest`):
      Khai báo kèm các annotation kiểm tra dữ liệu như `@NotBlank`, `@Min`, `@Email`.
    + Response DTOs (vd: `AuthResponse`, `OrderResponse`, `ProductDetailResponse`):
      Chứa dữ liệu chuẩn hoá đã được tính toán để Frontend vẽ lên giao diện.

4.3. SERVICE INTERFACE & SERVICE IMPL (*Service.java & *ServiceImpl.java)
  - VAI TRÒ: "Trái tim và khối óc" của hệ thống - nơi hiện thực hoá bài toán thực tế.
  - TẠI SAO TÁCH INTERFACE VÀ IMPL?
    + Tính đóng gói (Encapsulation): Che giấu chi tiết cài đặt, chỉ công khai hợp đồng nghiệp vụ.
    + Dễ dàng Unit Test: Có thể mock Interface bằng Mockito mà không phụ thuộc code thật.
    + Đa hình (Polymorphism): Dễ dàng thay đổi giải pháp (ví dụ: đổi từ Cloudinary sang AWS S3)
      bằng cách tạo implementation mới mà không sửa 1 dòng code nào ở Controller.
  - QUẢN LÝ GIAO DỊCH (@Transactional):
    + Nếu quá trình đặt hàng gồm 4 bước (Tạo đơn -> Trừ giỏ hàng -> Lưu lịch sử -> Trừ voucher),
      chỉ cần 1 bước gặp sự cố, `@Transactional` sẽ tự động ROLLBACK toàn bộ về trạng thái cũ,
      đảm bảo tính toàn vẹn dữ liệu (ACID).

4.4. REPOSITORY (*Repository.java)
  - VAI TRÒ: "Cầu nối" truy xuất dữ liệu từ Database.
  - CÁC KỸ THUẬT SỬ DỤNG TRONG THUNDERFOOD:
    + Derived Query Methods: Spring Data JPA tự động dịch tên hàm thành câu SQL:
      * `findByEmail(String email)` -> `SELECT * FROM users WHERE email = ?`
      * `existsBySettingKey(String key)` -> `SELECT COUNT(*) > 0 FROM system_settings WHERE ...`
    + Custom Query (@Query / JPQL): Viết câu lệnh truy vấn nâng cao có JOIN nhiều bảng
      hoặc tính toán thống kê doanh thu.
    + Hỗ trợ phân trang: Nhận tham số `Pageable` và trả về `Page<T>` có sẵn metadata
      (tổng số trang, tổng số bản ghi).

4.5. ENTITY (*.java trong package entity)
  - VAI TRÒ: Đại diện cho cấu trúc một dòng dữ liệu (Row) trong bảng MySQL.
  - CÁC ANNOTATION QUAN TRỌNG:
    + `@Entity`, `@Table(name = "...")`: Định danh bảng.
    + `@Id`, `@GeneratedValue(strategy = GenerationType.IDENTITY)`: Khoá chính tự tăng.
    + `@ManyToOne`, `@OneToMany`, `@JoinColumn`: Thiết lập quan hệ khoá ngoại (Foreign Key)
      giữa các bảng (vd: 1 Order có nhiều OrderItem).
    + `@CreationTimestamp`: Hibernate tự động ghi nhận thời gian tạo bản ghi.

4.6. CONFIG & SECURITY (*Config.java, SecurityUtils...)
  - VAI TRÒ: Thiết lập hạ tầng và luật chơi bảo mật cho toàn hệ thống.
  - `SecurityConfig`: Cấu hình SecurityFilterChain, CORS (cho phép frontend gọi API),
    CSRF disable, định nghĩa Route nào là Public (không cần token), Route nào yêu cầu
    vai trò `ADMIN` hay `STAFF`.
  - `JwtAuthenticationFilter`: Chạy trước mỗi request, trích xuất chuỗi token từ Header,
    giải mã lấy username/roles, nạp vào `SecurityContextHolder`.
  - `SecurityUtils`: Tiện ích giúp Service lấy nhanh ID của người dùng đang đăng nhập
    hiện tại mà không cần truyền `userId` từ Controller qua.

4.7. GLOBAL EXCEPTION HANDLER (GlobalExceptionHandler.java)
  - VAI TRÒ: "Lưới đỡ lỗi" tập trung cho toàn bộ ứng dụng.
  - Sử dụng `@RestControllerAdvice` và `@ExceptionHandler`.
  - Thay vì để server ném ra màn hình mã lỗi 500 kèm Stacktrace loằng ngoằng khó hiểu,
    handler này chặn lại và chuyển hoá thành JSON `ApiResponse` thân thiện:
    + Lỗi sai thông tin form -> 400 Bad Request kèm chi tiết lỗi từng trường.
    + Lỗi không tìm thấy id -> 404 Not Found.
    + Lỗi không có quyền -> 403 Forbidden.
    + Lỗi sai mật khẩu -> 401 Unauthorized.

PHẦN 5: CÁC LUỒNG VẬN HÀNH XUYÊN SUỐT (REQUEST LIFECYCLE & DATA FLOW)
================================================================================

Hiểu được cách các file phối hợp nhịp nhàng với nhau trong từng trường hợp thực tế
sẽ giúp bạn nắm chắc dự án. Dưới đây là 3 luồng vận hành cốt lõi:

--------------------------------------------------------------------------------
5.1. LUỒNG 1: XỬ LÝ MỘT REQUEST ĐÒI HỎI BẢO MẬT (Ví dụ: Thêm món vào giỏ hàng)
--------------------------------------------------------------------------------
1. Client gửi: `POST /api/v1/cart/items` kèm Header `Authorization: Bearer <jwt>`
   và Body `{ "productId": 101, "quantity": 2 }`.
2. `JwtAuthenticationFilter` chặn request:
   - Cắt chuỗi lấy token -> Gọi `JwtService.validateToken(token)`.
   - Token hợp lệ -> Lấy email người dùng -> Gọi `UserDetailsServiceImpl.loadUserByUsername()`.
   - Nạp thông tin xác thực vào `SecurityContextHolder`.
3. `SecurityConfig` kiểm tra: Route `/api/v1/cart/**` yêu cầu `authenticated()` -> Cho qua.
4. `CartController` tiếp nhận:
   - `@Valid` kiểm tra: `quantity` phải >= 1.
   - Gọi `SecurityUtils.getCurrentUserId()` để lấy ID khách hàng.
   - Gọi `cartService.addToCart(userId, request)`.
5. `CartServiceImpl` thực thi logic:
   - Kiểm tra món ăn có tồn tại và đang mở bán không (`productRepository.findById`).
   - Tìm giỏ hàng hiện tại của user (`cartRepository.findByUserId`).
   - Nếu món đã có trong giỏ -> Cộng dồn số lượng; nếu chưa có -> Tạo `CartItem` mới.
   - Lưu vào database qua `cartItemRepository.save()`.
   - Chuyển đổi Entity sang `CartResponse` DTO.
6. `CartController` nhận kết quả -> Trả về `ResponseEntity.ok(ApiResponse.success(data))`.

--------------------------------------------------------------------------------
5.2. LUỒNG 2: NGHIỆP VỤ CHECKOUT & ĐẶT HÀNG (Transactions & Dual-Voucher)
--------------------------------------------------------------------------------
1. Xem trước tính tiền (`POST /api/v1/orders/checkout/preview`):
   - `OrderServiceImpl` kiểm tra giỏ hàng có món hay không.
   - Xác thực địa chỉ giao hàng có thuộc Phường/Xã nằm trong danh sách phục vụ
     (`ServiceWard`) hay không.
   - Lấy phí ship mặc định và ngưỡng miễn phí ship từ `SystemSetting`.
   - Áp dụng kiểm tra đồng thời Voucher món và Voucher vận chuyển (`VoucherService`).
   - Trả về bảng phân tích chi phí chi tiết cho khách hàng xem trước.
2. Đặt hàng chính thức (`POST /api/v1/orders/checkout`):
   - Mở Transaction `@Transactional`.
   - Sinh mã đơn hàng duy nhất (Unique Order Code dạng `THUNDER-XXXXXX`).
   - Khởi tạo đơn hàng `Order` với trạng thái ban đầu: `PENDING`.
   - Chuyển toàn bộ món từ `CartItem` sang bảng `OrderItem`.
   - Xoá rỗng giỏ hàng của khách hàng.
   - Ghi nhận lượt sử dụng vào bảng `VoucherUsage` (tăng biến đếm `usedCount` của voucher).
   - Ghi nhận lịch sử vào bảng `OrderStatusHistory` ("Đơn hàng mới được tạo").
   - Commit Transaction. Nếu bất kỳ lỗi nào xảy ra -> Tự động Rollback, không mất dữ liệu.

--------------------------------------------------------------------------------
5.3. LUỒNG 3: VẬN HÀNH LOGISTICS - GOM GÓI HÀNG (Delivery Package Workflow)
--------------------------------------------------------------------------------
1. Khách đặt các đơn hàng lẻ tẻ tại các phường lân cận.
2. Nhân viên điều phối / Bếp gom tối đa 7 đơn hàng (theo `max_orders`) vào chung một
   gói hàng có tên duy nhất (ví dụ: "Gói Hoàn Kiếm Trưa 01").
   - Entity `DeliveryPackage` được tạo với trạng thái `PENDING`.
   - Các đơn hàng được gán khoá ngoại `delivery_package_id = package.id`.
3. Shipper/Nhân viên đăng nhập vào Cổng Staff:
   - Xem danh sách các gói hàng đang chờ nhận.
   - Bấm "Nhận giao gói": Hệ thống kiểm tra Shipper đó hiện tại có đang giao dở gói
     nào không. Nếu chưa -> Gán `shipped_by_staff_id = shipper.id`, đổi trạng thái
     gói sang `DELIVERING`.
4. Shipper đi giao từng đơn trong gói:
   - Cập nhật trạng thái từng đơn: `DELIVERING` -> `DELIVERED` (hoặc `CANCELLED` nếu khách boom hàng).
   - Khi tất cả đơn bên trong gói đều đã đạt trạng thái cuối -> Gói hàng tự động chuyển
     sang `COMPLETED` và ghi nhận `completed_at`. Lúc này Shipper mới được nhận gói mới.

================================================================================
PHẦN 6: BẢN ĐỒ DỮ LIỆU & CÁC THỰC THỂ NGHIỆP VỤ (DATABASE ENTITIES MAP)
================================================================================

Dưới đây là danh sách 21 Entities và mối quan hệ nghiệp vụ trong MySQL:

[ NHÓM TÀI KHOẢN & BẢO MẬT ]
  1. `User`: Tài khoản người dùng (email, password hash BCrypt, fullName, phone, role...).
  2. `Role`: Phân quyền (ADMIN, STAFF, CUSTOMER).
  3. `UserToken`: Quản lý Refresh Token và mã OTP khôi phục mật khẩu.

[ NHÓM MÓN ĂN & THỰC ĐƠN (CATALOG) ]
  4. `Category`: Danh mục món ăn (Cơm, Mì, Đồ uống, Tráng miệng...).
  5. `Product`: Món ăn (tên, slug, giá bán, giá gốc, mô tả, soldCount, ratingAverage...).
  6. `ProductImage`: Thư viện ảnh của món ăn (link Cloudinary, cờ ảnh đại diện).
  7. `Review`: Đánh giá sao (1-5) và bình luận của khách hàng sau khi hoàn tất đơn.
  8. `Wishlist`: Danh sách món ăn yêu thích của khách hàng.

[ NHÓM GIỎ HÀNG & MÃ KHUYẾN MÃI ]
  9. `Cart`: Giỏ hàng của từng khách hàng (quan hệ 1-1 với User).
 10. `CartItem`: Từng món ăn và số lượng chọn trong giỏ hàng.
 11. `Voucher`: Mã giảm giá (loại giảm %, giảm tiền mặt; mục tiêu giảm tiền món hay tiền ship).
 12. `VoucherUsage`: Nhật ký lưu trữ user nào đã dùng voucher nào cho đơn hàng nào.

[ NHÓM ĐƠN HÀNG & GIAO VẬN (ORDERS & LOGISTICS) ]
 13. `Order`: Đơn hàng trung tâm (orderCode, subtotal, discount, shippingFee, totalAmount...).
 14. `OrderItem`: Chi tiết món ăn bên trong đơn (lưu snapshot tên món và giá tại thời điểm mua).
 15. `OrderStatusHistory`: Dòng thời gian lịch sử trạng thái đơn (PENDING -> PREPARING -> DELIVERING...).
 16. `DeliveryPackage`: Gói hàng gom nhiều đơn để Shipper nhận giao theo lộ trình.
 17. `Payment`: Bản ghi thanh toán (COD, VNPAY, MOMO, trạng thái PENDING/SUCCESS).

[ NHÓM ĐỊA CHỈ & HỆ THỐNG ]
 18. `Address`: Sổ địa chỉ nhận hàng của khách hàng.
 19. `ServiceWard`: Danh mục Phường/Xã có hỗ trợ giao hàng và đơn giá ship khu vực.
 20. `SystemSetting`: Cấu hình toàn hệ thống (phí ship sàn, ngưỡng freeship, địa chỉ bếp...).
 21. `Banner` & `Notification`: Quản lý banner quảng cáo và thông báo gửi đến người dùng.

================================================================================
PHẦN 7: LỘ TRÌNH HỌC TẬP TỪNG BƯỚC & GỢI Ý CÂU HỎI THẢO LUẬN
================================================================================

Để đạt hiệu quả cao nhất, chúng ta sẽ lần lượt đi qua các chặng sau trong các buổi học tới:

CHẶNG 1: NỀN TẢNG BẢO MẬT & XÁC THỰC (Security & Auth)
  - Tìm hiểu cách `JwtAuthenticationFilter` chặn bắt và trích xuất Claims.
  - Cơ chế mã hoá mật khẩu BCrypt và chống tấn công dò quét.
  - Chu trình cấp mới Access Token qua Refresh Token.
  * Câu hỏi suy ngẫm: Tại sao Refresh Token lại được lưu vào Database (`user_tokens`)
    trong khi Access Token thì không cần lưu?

CHẶNG 2: THỰC ĐƠN & TỐI ƯU TRUY VẤN (Catalog & JPA Query)
  - Cách triển khai bộ lọc đa điều kiện (Category, Price Range, Rating, Sorting).
  - Kỹ thuật tính toán số lượng bán và cập nhật điểm đánh giá trung bình.
  - Tạo SEO friendly slug tiếng Việt.
  * Câu hỏi suy ngẫm: Làm thế nào để giải quyết bài toán N+1 Query khi lấy danh sách
    món ăn kèm theo danh sách hình ảnh của từng món?

CHẶNG 3: GIỎ HÀNG & THUẬT TOÁN TÍNH TIỀN CHECKOUT (Cart & Pricing Logic)
  - Cách tính toán kiểm tra điều kiện áp dụng của 2 loại Voucher cùng lúc.
  - Giải thuật kiểm tra ngưỡng Miễn phí vận chuyển (Free Shipping Threshold).
  * Câu hỏi suy ngẫm: Nếu 2 khách hàng cùng áp dụng 1 voucher chỉ còn đúng 1 lượt dùng
    vào cùng một phần nghìn giây, backend xử lý concurrency như thế nào?

CHẶNG 4: QUẢN LÝ GIAO DỊCH & LOGISTICS GOM ĐƠN (Orders & Packages)
  - Cơ chế `@Transactional` và Rollback khi có lỗi xảy ra.
  - Thuật toán gom đơn vào `DeliveryPackage` và cơ chế khoá nhận gói của Shipper.
  - Ghi nhận Audit Log lịch sử đơn hàng (`OrderStatusHistory`).

CHẶNG 5: TÁC VỤ NGẦM & TÍCH HỢP BÊN NGOÀI (Schedulers & 3rd Services)
  - Cách cấu hình Spring Task Scheduling dọn dẹp token rác.
  - Tích hợp Cloudinary tải ảnh và Gmail SMTP gửi thư.
